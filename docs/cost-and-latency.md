# 成本与延迟账本

> 这份文档回答两个面试里最常被追问、学生项目却最少回答的问题：**一次提问花多少钱？一次回答等多久？**
>
> **口径**：token 与延迟全部来自**本机生产链路实测**（`eval/run_eval_l2.py` 走的是线上同一套
> `ChatService`：路由 → 检索 → Agent（含有界工具循环）→ 带来源回答）；单价取自**公开资料**的
> DeepSeek 定价，**未与官方定价页逐项核对**；换算按 `1 USD ≈ 7.1 CNY`。
> 数据出处：[`eval-report-l2.md`](eval-report-l2.md)（私人语料 46 条）、
> [`eval-report-l2-synthetic.md`](eval-report-l2-synthetic.md)（自产合成语料 30 条）、
> [`retrieval-diagnosis.md`](retrieval-diagnosis.md)（嵌入延迟）。

## 0. 一句话结论

**LLM 是这套系统里最便宜的一环**：一次带检索上下文的提问约 **1 分钱**，跑完整套 L2 生成层评测
（30–46 条，含 LLM-as-judge）**不到 1 元**。真正的开销在**时间**（本地嵌入的建索引 CPU 时间、端到端
约 5.6 s 的等待）和**一次性的模型分发体积**（2.2 GB）——所以这里花钱买不到什么，优化空间在体验。

## 1. 一次性成本

| 项 | 数值 | 出处 / 说明 |
|---|---|---|
| Embedding 模型分发 | `intfloat/multilingual-e5-large`，**2.2 GB** | 本地 `fastembed`（ONNX），换模型 = 重新分发 |
| 模型首次加载 | 2.3 s | 冷启动一次，之后常驻 |
| 建索引（一次性，随语料） | 私人语料 **408 片段 112 s**；合成语料 154 页 / 189 片段 **约 72 s**（首份含冷读 36.4 s） | `retrieval-diagnosis` §3.7；本次 L2 运行的摄取日志 |
| API 侧的一次性成本 | **0** | 嵌入全在本地，不产生 token 账单 |
| 生产库体积 | **11.8 MB**（5 文档 / 315 片段 / 56 条 trace） | `backend-python/data/*.sqlite3` |

> 2.2 GB 是这套方案最"重"的代价：它不是钱，是**分发与首次启动的摩擦**。评测反复跑（L1 完全离线）
> 之所以能零成本，就是拿这个体积换来的。

## 2. 每次提问的可变成本

单价（deepseek-flash 档，公开资料；**峰谷分时**，高峰费率为平峰两倍）：

| | 输入（缓存未命中） | 输出 |
|---|---|---|
| 平峰 | $0.22 / 百万 token | $0.66 / 百万 token |
| 高峰 | $0.44 / 百万 token | $1.32 / 百万 token |

| 语料 | 输入 token（均） | 输出 token（均） | 单次成本（平峰） | 折人民币 |
|---|---|---|---|---|
| 私人语料（46 条） | 4,388 | 611 | **$0.00137** | **≈ ¥0.01** |
| 自产合成语料（30 条） | 3,457 | 513 | **$0.00110** | **≈ ¥0.008** |

> 输入 token 里绝大部分是**检索上下文**（`top_k=20`）：这正是"该不该把 20 条都喂进去"这类
> 取舍要算的账 —— 而实测（假设 #9）显示 4.4k 输入的上下文**没有**撑爆或超时，代价可接受。
> 输出 token 稳定在 0.5–0.6k，说明"简洁作答"的提示词约束是有效的。

## 3. 跑一次评测要多少钱

| 评测 | LLM 成本 | 说明 |
|---|---|---|
| **L1 检索层**（`eval/run_eval.py`） | **0** | 不调 LLM，纯本地嵌入 + vec0 KNN，完全可重复 |
| **L2 生成层**（`eval/run_eval_l2.py`，私人 46 条） | **≈ $0.063（¥0.45）** | 46 × (4,388 in + 611 out) |
| **L2 生成层**（合成 30 条） | **≈ $0.033（¥0.23）** | 30 × (3,457 in + 513 out) |
| 上表的 L2 **加上** LLM-as-judge | **量级仍 ≤ ¥1** | judge 每题多一次调用；未逐条计量，故只给量级 |

> **这也是"L1/L2 分层"的动机**：改切块、换模型、调 `top_k` 这类高频实验全部落在 L1 —— 零成本、
> 秒级、完全确定；只有"答案好不好"这种必须过 LLM 的问题才进 L2，且一次不到一块钱。

## 4. 性能账

| 指标 | 值 | 出处 |
|---|---|---|
| 解析 + 切块 + 嵌入（摄取） | 合成语料 6 份 PDF / 154 页：**约 72 s**（首份含模型冷读 36.4 s，稳态约 **7 s/份**） | 本次 L2 运行日志 |
| Query 嵌入 | **30 ms** | `retrieval-diagnosis` §3.7 |
| 向量检索（vec0 KNN） | **未单独计时** | 端到端延迟里占比小（见下），未做拆分 |
| 端到端总延迟 P50 / P95（私人语料） | **5,468 ms / 10,602 ms** | `eval-report-l2.md` §四 |
| 端到端总延迟 P50 / P95（合成语料） | **5,642 ms / 11,318 ms** | `eval-report-l2-synthetic.md` §四 |
| **TTFT（首字延迟）** | **未测** | 当前**没有流式**，拿不到首字时间 —— 见 §6 |
| 上传 | 受理即返回（202 + `job_id`），前端轮询进度 | `docs/specs/us-stage1-upload-async.md` |

> ⚠️ 上面的"端到端延迟"是**从提问到拿到完整回答**的整段等待，**不是 TTFT**。两者常被混为一谈：
> 5.6 s 的整段等待在对话体验里是"卡"，但若首字只要 0.5 s，感受完全不同 —— 而这正是流式要解决的问题。

## 5. 已经做过的优化与它们的代价

| 优化 | 收益（实测） | 代价 |
|---|---|---|
| Embedding 从 `MiniLM-L12-v2` 换成 `multilingual-e5-large` | 中文 @20 **91.7% → 100%**、法语 @5 **50% → 83.3%**、MRR +0.34；顺带解决 128-token 截断（截断率 39.5% → 0%） | 模型 0.22 GB → **2.2 GB**；维度 384 → 1024（换维度必须重建 vec0 索引）；query 嵌入 4 ms → 30 ms |
| `top_k` 5 → 20 | 中文 HitRate@5 50% → **@20 91.7%** | 上下文片段数 ×4；实测 20 条约 7,800 字符，**未触发** `CONTEXT_MAX_CHARS=8000` 预算 |
| 解析阶段还原法语重音（`PDFParser` 1.1.0） | 修复 1,580 处拆裂；超 128 token 片段 39.5% → 28.2%；中文 @20 +8.3pp | 解析器一处规则 + 8 个单测 |
| 提示词强制 `[来源 N]` 记号（与 `ContextBuilder.render()` 对齐） | 带引用的答案 **35% → 100%**；引用召回率 **21.1% → 77.8%** | 无（纯提示词修正，但此前一直没被发现） |
| 上传异步化 + 进度反馈 | 长文档不再阻塞请求 | 多一张 `ingest_jobs` 表 + 轮询 |

> 一条方法论：以上每一项都**先有测量、再有改动**。`top_k` 那次尤其典型 —— 直觉以为"调大
> `top_k` 会让上下文 4 倍膨胀、必须靠预算兜底"，实测发现 20 条只有约 7,800 字符，**预算根本没触发**。

## 6. 还没做的（下一版的账）

| 待做 | 预期收益 | 为什么还没做 |
|---|---|---|
| **流式输出** | 让 TTFT 可测、可优化；把 5.6 s 的"卡"变成"逐步出字" | 需要 provider 层支持 `stream`，改动面比想象大（Agent 工具循环 + 流式叠加） |
| 查询缓存 | 相同/相似 query 命中即零成本 | 单机 demo 场景收益低，先不做 |
| 对话历史窗口 | 降低多轮输入 token | 当前评测全是单轮，没有多轮数据支撑该不该做 |
| 小模型路由（简单问题走小模型） | 单次成本再降 | 一次提问才 1 分钱，**成本不是当前瓶颈** |

## 7. 口径与限制

1. **单价不是官方页面数值**：来自公开资料汇总，且 DeepSeek 采用峰谷分时计价 + 缓存命中折扣
   （命中价约为未命中的 1/30），实际账单会低于上表估算；要写进简历请以官方定价页核对。
2. **token 是 provider 回传的均值**，不是逐条精确值；provider 不回传时评测会明确写"未回传"而不是填 0。
3. **延迟含生成层随机性**（temperature > 0），跨次比较看量级与分层，不要当常数。
4. **没有做 `faithfulness`（每句话是否都被引用支持）的计量** —— 引用口径只到"引到的页在不在期望页里"。
5. **单机 SQLite、无并发**：这里的成本/延迟都是单人单机视角，**不构成规模化结论**
   （企业关心的 P99、并发成本、千万级文档下的表现，本项目没有素材）。

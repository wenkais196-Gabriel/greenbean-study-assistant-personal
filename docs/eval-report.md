# 评测报告 · 跨语言检索首测（阶段 1 收尾）

> 实验日期：**2026-09-12** ｜ 脚本：[`backend-python/scripts/experiment_chunk_size.py`](../backend-python/scripts/experiment_chunk_size.py)
> 目的：回答 [`planning/STATUS.md`](../planning/STATUS.md) §五 的**假设 #1**（中文 query 能否检索到法文 chunk）与 **假设 #7**（`chunk_size` 该取多少）

---

## 0. 结论摘要（三句话）

1. **假设 #1 不成立**：中文提问 → 法文资料的 **HitRate@5 只有 41.7%–50%**。**近一半的问题找不到正确片段。**
   → 因此 **"跨语言语义检索有效"不得写进 README / 简历 / 面试话术**。
2. **假设 #7 的答案与直觉相反**：`chunk_size=300` **最差**（41.7%），500 与 800 打平（50%）。
   "块更小更安全"的推断**被数据否定** —— 块太小使语义信息不足，损失超过"超出模型 token 上限被截断"的损失。
3. **当前瓶颈不在切块参数，而在检索本身**：无论怎么切，都有一半查询召回不到期望片段。
   下一步该验证的是**更强的多语言模型**与**混合检索 / 重排**，而不是继续调 `chunk_size`。

## 1. 方法

| 项 | 值 |
|---|---|
| 语料 | 5 份真实法语 AI 课程资料（PDF，共 **290 页**）：`00-Intro-IA`、`01-Recherche-Arborescente`、`01_Intro ML`、`02-SAT-CSP`、`02_intro supervise` |
| 语料来源 | 用户提供的本地资料，**未入库、未上传**（实验直接读原路径） |
| 切块 | `ChunkService`，`chunk_size ∈ {300, 500, 800}`，`overlap = chunk_size / 8` |
| 嵌入 | `sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2`（384 维，fastembed 本地推理） |
| 索引 | `sqlite-vec` vec0 虚拟表（本地 KNN，**非平方 L2**，见 §2.2） |
| 查询 | **12 条中文提问**（覆盖 5 份资料的术语与概念） |
| 判定 | 期望来源 = 含指定法文关键词的 chunk；看它是否落在 **top-5** 召回里 |
| 指标 | **HitRate@5 = 命中 / 可判定样本** |

### 1.1 口径说明（这里是本次最值得记录的方法学教训）

第一版报告把"关键词在提取文本里找不到"的查询**当作未命中**，得出一张偏低的表；
第二版又误以为那些条目是"评测没构造好"，一度得出"可判定样本 100% 命中"的相反结论；
**第三版在匹配前对空白做归一（把换行/多空格折叠成单空格）后，所有 12 条都成为可判定样本**，结果回到 41.7%–50%。

> **教训**：`HitRate` 的分母必须写清楚是"全部查询"还是"可判定查询"，
> 并且**匹配逻辑本身要先验证**——否则评测会给出方向完全相反的结论。
> 现在脚本会把"无法判定"单独计数，不再混进"未命中"。

### 1.2 一个必须记录的解析问题

PyMuPDF 从这批幻灯片 PDF 提取文本时，**法语重音被拆成独立符号**（`à` → `` `a ``、`général` → `g´en´eral`），
且**幻灯片标题常被换行切开**（`Recherche\nArborescente`）。

- 这**直接影响嵌入质量**（`g´en´eral` 与 `général` 对模型是不同的 token 序列）；
- 而这部分正是**解析器**的职责（也是我在上游 PR #26 里写的代码）；
- 本次实验用"归一化后匹配"绕过了它，但**生产链路里没有修** → 已登记为待办。

> 这个量级的距离说明"最相似的片段其实也**并不很像**"——即召回质量低是**整体性的**，
> 不是个别 query 的偶然。

### 2.2 更正：vec0 的距离是「非平方 L2」

本报告（以及当时的设计文档）把 vec0 的距离写成「L2 平方距离」，**这是错的**。
2026-09-12 的诊断实验实测：vec0 v0.1.9 返回的是**非平方的 L2（欧氏距离）**
—— 与自算平方 L2 的最大偏差 9.906、与自算欧氏距离的最大偏差 0.000001
（见 [`retrieval-diagnosis.md`](retrieval-diagnosis.md) §3.4）。

上表的数值与"命中/未命中"结论**不受影响**（平方与非平方只差一个单调变换，不改变排序），
但**阈值口径**受影响（`RETRIEVAL_MAX_DISTANCE` 不能按平方 L2 估），故在此更正。

## 3. 失败案例分析（6 条未中）

| 案例 | 可能原因 | 可验证的改进 |
|---|---|---|
| #1 监督学习 / #2 kNN / #4 随机森林 / #7 树搜索 | 这些是**资料的核心主题**（整份 PPT 都在讲），期望 chunk 集合很大，却仍未进入 top-5 —— 指向**中法语义对齐能力不足**（MiniLM 是小模型，跨语言对齐弱） | 换更强的多语言模型（如 `multilingual-e5-large`，1024 维）；或加 **BM25 混合检索** |
| #8 可满足性（`satisfi`） | `satisfi` 是**词干**（satisfiabilité / satisfiable），而模型的向量是整体语义；中文"可满足性"与该词干在多语言空间里可能不相邻 | 术语表映射；或查询改写（query expansion） |
| #11 课程整体内容（`contenu`） | "课程整体会讲什么"太**泛**，与任何具体片段的相似度都不高 | 引入**摘要/目录级索引**；或对泛问题走"结构类"路由（现有 `RouterAgent` 的 `STRUCTURE`） |

**共同点**：这些都是**真实的用户会问的问题**，不是刻意构造的难题。也就是说，
**50% 的命中率不是实验设计的偏差，而是当前方案的真实水平。**

## 4. 局限（必须说清楚，避免过度解读）

1. **样本小**：12 条查询、5 份资料。结论方向可信，具体数值不宜当精确指标。
2. **单一模型**：只测了 `paraphrase-multilingual-MiniLM-L12-v2`，没有对照其他模型。
3. **单一检索方式**：纯向量检索，**没有**混合检索（BM25）与重排（reranker）。
4. **单一切块方式**：只调了 `chunk_size`，没有对照"段落优先 vs 固定窗口"。
5. **判定偏严**：要求期望 chunk 进入 top-5；若放宽到 top-10，命中率会上升（但用户能容忍的 top-k 有限）。
6. **`chunk_size` 与模型 128 token 上限的张力仍未单独隔离**（三个尺寸都有截断可能）。

## 5. 下一步（按预期收益排序）

| # | 动作 | 为什么 | 成本 |
|---|---|---|---|
| **1** | **换更强的多语言模型做对照**（如 `intfloat/multilingual-e5-large`，1024 维） | 6 条失败里 4 条指向"语义对齐太弱"，这是最直接的怀疑对象 | 中（模型更大、向量库要重建） |
| **2** | **加混合检索**（向量 + BM25/关键词并集） | `satisfi`、`contenu`、`recherche arborescente` 这类**关键词性强**的查询，稀疏检索往往直接命中 | 中 |
| **3** | **修解析器的重音问题**（`´e` → `é`） | 直接影响嵌入质量，且是**我自己的模块** | 低 |
| **4** | **扩大评测集**（12 → 30–50 条，并补"无答案"类） | 让结论更有统计意义，同时是阶段 3 评测集的基础 | 中 |
| **5** | 加 reranker | 在候选里重排，理论上提升精度 | 中（+100–300ms 延迟） |
| **6** | 继续调 `chunk_size` | **数据已表明收益不大**，优先级最低 | 低 |

> **面试叙事价值**：这份报告本身就是"技术选型必须用数据验证"的完整案例——
> 选模型时看了体积、语言覆盖、离线能力，漏看了跨语言对齐质量；
> 而**是评测把这个漏看暴露出来的**，不是直觉。

# 诊断报告 · 中文提问检索法文资料，命中率低在哪一环

> 实验日期：**2026-09-12** ｜ 脚本：[`backend-python/scripts/experiment_diagnosis.py`](../backend-python/scripts/experiment_diagnosis.py)
> 上游首测：[`docs/eval-report.md`](eval-report.md)（只测了 `chunk_size`，结论停在"跨语言语义对齐不足"）
> 目的：把首测**未隔离**的三个变量（语料污染 / 检索度量 / 查询语言）拆成可对照的条件，找出真正的瓶颈

---

## 0. 结论摘要（四句话）

1. **"跨语言"不是主因**：同一批语料、同一管线，**法语提问的 HitRate@5 只有 58.3%**（L2）/ 66.7%（cos），
   中文提问 50.0% —— 换回母语只多 8.3pp。**瓶颈在检索本身，不在语言跨度。**
   → 首测把失败归因于"跨语言语义对齐不足"，**该归因需要修正**。
2. **失败样本大多没排到前面，而不是召不到**：中文提问在 `@5` 只有 50%，但放宽到 `@20` 达 **83.3%**（修重音后 **91.7%**），
   12 条里只有 **1 条**真正召不回。→ **`top_k=5` 过窄 + 排序区分度弱**，是当前最直接的可修项。
3. **两个曾被认为最可疑的因素，都被数据否定**：改 cosine **@5 最多 +8.3pp**；
   修重音 **@5 无变化**（@20 才 +8.3pp）。两者都是真实缺陷，但**都不解释 50% 的天花板**。
4. **确诊三个客观缺陷**（该修，但都不是天花板）：**39.5% 的片段超模型 128 token 上限被截断**；
   语料有 **1580 处**重音拆裂；`vec0` 返回的是**非平方欧氏距离**（注释与阈值口径写错了）。

### 0.1 本报告结论的落地状态（2026-09-12 同日）

| 建议 | 状态 |
|---|---|
| `RETRIEVAL_TOP_K` 5 → 20 | ✅ 已实施（`app/config/settings.py`） |
| 解析阶段还原重音 | ✅ 已实施（`app/utils/text_utils.repair_broken_accents` + `PDFParser` 升到 1.1.0，处数写入 `metadata.accent_repairs`） |
| 更正 vec0 距离口径 | ✅ 已实施（代码注释 + 本报告 + [`eval-report.md`](eval-report.md) §2.2 + 两份 spec） |
| `top_k=20` 的代价侧：上下文预算裁剪 | ✅ 已实施（`ContextBuilder.build_within_budget`，`CONTEXT_MAX_CHARS=8000` 软上限；spec AC11/AC12） |
| 换更强的多语言模型 / 混合检索 / token 感知切块 | ⬜ 未实施（见 §5） |

**生产链路校验**：本报告数据由 `experiment_diagnosis.py` 的 `verify_production_parser()` 逐页比对 ——
生产 `PDFParser` 的输出与 `repair_broken_accents(raw)` **290 页全部一致**。
因此下表的 `repaired` 条件就是**线上实际行为**，而不是脚本里的另一份实现。

## 1. 方法

| 项 | 值 |
|---|---|
| 语料 | 与首测同一批 5 份法语课程 PDF（290 页 / 130,241 字符 / 408 个 chunk） |
| 文本提取 | `raw` = PyMuPDF 原样提取（等价于修复前的解析行为）；`repaired` = 对 raw 调用**生产实现** |
| 切块 | `ChunkService`，`chunk_size=500`、`overlap=62`（首测：500 与 800 打平，取 500） |
| 嵌入 | `sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2`（384 维，fastembed 0.8.0） |
| 查询 | 中文 12 条（沿用首测）+ **法语 12 条**（与中文一一对应同一期望关键词） |
| 判定 | 沿用首测口径：期望来源 = 归一化后含指定法文关键词的 chunk；命中 = 进入 top-k |
| 指标 | **HitRate@1/3/5/10/20、MRR、期望片段的最佳排名**（排名用于区分"排错"与"没召回"） |

### 条件矩阵（8 个条件）

| 变量 | 取值 | 为什么 |
|---|---|---|
| 语料文本 | `raw` / `repaired` | `raw` = PyMuPDF 原样提取；`repaired` = 对 raw 调用**生产实现** `app.utils.text_utils.repair_broken_accents`（诊断与线上同源） |
| 检索度量 | `L2`（现状，vec0 KNN）/ `cos`（自算余弦） | 实测向量**未归一化**，怀疑 L2 被范数污染 |
| 查询语言 | 中文 / 法语 | 法语是**同语言上界基线**，用来判断"是不是跨语言的问题" |

## 3. 关键发现

### 3.1 「跨语言」不是主因（首测归因需修正）

法语提问只是把 @5 从 50.0% 抬到 58.3%（L2）/ 66.7%（cos）。**母语提问也有一半找不到**。
→ 首测 §3 把 4 条失败归因于"中法语义对齐能力不足"，缺的正是这个基线；
真实瓶颈是**通用语义检索区分度**，换更强的多语言模型仍然是对的方向，但**理由不是"跨语言"**。

### 3.2 排序区分度弱 + `top_k=5` 过窄（当前最大的可修项）

| 条件 | @5 | @10 | @20 |
|---|---|---|---|
| raw / L2 / 中文 | 50.0% | 58.3% | **83.3%** |
| repaired / L2 / 中文 | 50.0% | 75.0% | **91.7%** |

`@5 → @20` 多出 33.3~41.7pp，且 408 个片段里只牺牲精确率换来召回。
→ **提高 `top_k` 是零模型成本、立刻可验证的改动**；代价是上下文变长，需要用重排/精选来消化。

### 3.3 被数据否定的两个假说（诚实记录）

| 假说 | 预期 | 实测 | 判定 |
|---|---|---|---|
| **L2 被未归一化向量的范数污染，改 cosine 能救** | 大幅提升 | @5 最多 +8.3pp，MRR 互有胜负（0.408→0.352） | ❌ **不成立** |
| **重音拆裂污染语料向量，修了能救** | 大幅提升 | @5 无变化（50.0%→50.0%），@20 +8.3pp | ❌ **不是天花板原因**（但仍是真实缺陷） |

为什么余弦没救回来：同一 query 下 `L2² = |q|² + |d|² − 2q·d`，`|q|²` 是常数，
只剩 `|d|²` 项产生差异；而实测 chunk 范数分布**很集中**（p50=3.11、p90=3.90），
所以 L2 与 cos 的排序几乎一致。**范数污染是理论隐患，不是这次的病根。**

### 3.4 确诊的客观缺陷（该修，但不解释 50% 天花板）

| # | 缺陷 | 实测证据 | 影响 |
|---|---|---|---|
| 1 | **片段超模型 128 token 上限被截断** | raw：**161/408 = 39.5%** 超限（p50=107、p90=161、**max=205**）；修重音后降到 115/408（28.2%） | 近四成片段的尾部语义**从未进入向量** |
| 2 | **重音拆裂污染语料** | **1580 处**（`général`→`g´en´eral`、`à`→`` `a ``、`reconnaître`→`reconnaˆıtre`）；方向 336:0 全为"符号在字母前" | 词形失真；修后 max token 205→197、@20 +8.3pp |
| 3 | **`vec0` 距离语义与注释不符** | vec0 距离 vs 自算**平方** L2 偏差 **9.906**；vs 自算**欧氏**距离偏差 **0.000001** | `Retriever` / `EmbeddingRepository` 注释写的"L2 平方距离"是错的 → `RETRIEVAL_MAX_DISTANCE` 阈值语义会设错（不影响排序） |

### 3.5 判定口径本身偏宽

期望片段集合大小 **p50 = 7 个 chunk**（min 1、max 26）——即"只要召回任一个含关键词的片段就算命中"，
门槛相当宽松，命中率仍只有 50%~91.7%。→ **真实可用性不优于这张表。**

---

## 4. 结论

> **命中率低的根因是"嵌入模型的排序区分度不足"叠加"`top_k` 过窄"**，
> 而不是"中文↔法语跨语言"、不是"L2 度量"、也不是"重音污染"。
> 证据：母语提问也只有 58.3%；一半失败样本排在第 6~20 名；只有 1/12 条真的召不回。

## 6. 局限（避免过度解读）

1. **样本小**：12 条 query × 2 种语言；1 条 = 8.3pp，差异在 ±1 条的范围内就不要当结论。
2. **单一模型**：只测了 `MiniLM-L12-v2`；"换模型能提升多少"仍**未验证**。
3. **判定仍用关键词包含**：期望集合 p50=7，偏宽；且关键词命中不等于"语义上真正答对"。
4. **度量对照不完全对称**：L2 排名限 top-50（vec0 KNN），cos 为全量 408 → 对 cos 略有利，而 cos 依然没赢。
5. **未做**：混合检索、重排、模型对照、无答案类查询（拒答能力）、token 感知切块。
6. **单一 `chunk_size`**：本诊断固定 500（首测已证 500/800 打平、300 更差）。
7. **修复后的上层效果仍未测**：`top_k=20` 会让每次问答进入约 4 倍片段。已用 `ContextBuilder.build_within_budget`
   （`CONTEXT_MAX_CHARS=8000` 的**软上限**：超预算整片丢弃、至少留 1 条）钉住规模，
   但"预算该取多大""丢掉尾部片段会不会丢掉答案"必须由真实 LLM provider 度量 —— 本报告只覆盖召回侧。
